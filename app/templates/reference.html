Database Reference Notes

This page summarizes the key database design ideas behind the Warehouse Inventory Management System and highlights the main points that should be explained during presentation.

Core Entities and Relationships

This application mirrors the warehouse model using the following core entities: Item, Category, Supplier, Warehouse, Location, StockTransaction, PurchaseOrder, PurchaseOrderItem, User, and ItemSupplier.

  • Item → Category is many-to-one.
  • Item ↔ Supplier is many-to-many through ItemSupplier.
  • Location → Warehouse is many-to-one.
  • StockTransaction → Item and StockTransaction → User are many-to-one.
  • PurchaseOrder → Supplier and PurchaseOrder → User are many-to-one.
  • PurchaseOrderItem → PurchaseOrder and PurchaseOrderItem → Item are many-to-one.

Why PostgreSQL Matters Here

PostgreSQL provides the relational foundation that makes the system reliable and defensible. Primary keys uniquely identify records, foreign keys enforce relationships, numeric fields support price values, and timestamps preserve transaction history. These are the parts that keep the application consistent instead of turning it into guesswork with buttons.

Why the Design is Normalized

The schema is structured to reduce redundancy and improve consistency. Categories, suppliers, warehouses, and locations are stored separately instead of being repeated in the item table. The many-to-many relationship between items and suppliers is resolved using the ItemSupplier table, and purchase order lines are separated into PurchaseOrderItem so that each order can contain multiple items without repeating columns.

What to Explain During Presentation

  1. Show the ERD and map each relationship to an actual table and foreign key.
  2. Explain why ItemSupplier exists instead of storing supplier data directly inside Item.
  3. Show how StockTransaction preserves history instead of overwriting stock movement.
  4. Explain one report and describe the joins used to produce it.
  5. Discuss how the schema supports 1NF, 2NF, and 3NF.
  6. Explain how role-based access control supports operational discipline and data integrity.
